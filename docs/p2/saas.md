# Member 2: platform design and validation

The SaaS authenticates exact request bytes using collector keys and HMAC. The credential determines tenant, collector, and region; the service also checks that payload references agree. The frozen JSON Schema plus semantic validation reject fields outside the metadata contract. A non-privileged database role sets tenant context per transaction and Postgres RLS applies to reads and writes. The app remains a trusted boundary: RLS is not protection against arbitrary SQL execution with the application role.

Two stateless replicas in one region can share a database. The database stores unique IDs and serializes transactions per tenant, so retries across replicas deduplicate and same-ID/different-body conflicts are returned. This per-tenant lock is a throughput limit. Separate region-bound databases prevent accidental startup of an `eu` replica against an `in` database; geographic deployment, routing and data residency still require separate infrastructure.

The ontology provides typed tenant, collector, source, observation, incident, recommendation and action views. Incident signals retain `payload_id`; the dashboard can follow these links and inspect metadata, but not raw logs. Detection uses a rolling median/MAD and requires two consecutive event-time windows before emitting a baseline anomaly. Critical static thresholds and security summaries can alert immediately. Events arriving out of order are stored but cannot rewrite the current persistence streak. Related signals for the same collector/source within 120 seconds are grouped; heuristic confidence is based on distinct signal types. Neither correlation nor confidence proves causation.

The action lifecycle is simulated: an operator proposes a validated action, approves or rejects it, and can record a rollback after approval. Each transition is tenant-scoped and audited, with a rollback plan. No infrastructure commands run. Admin-created short-lived enrollment tokens issue a collector key and HMAC secret once. The token and key are stored as hashes; the HMAC secret is stored in the scoped database for verification. This is a prototype: use TLS, secret encryption, rotation/revocation, rate limits, and individual user identities before production.

The dashboard uses authenticated SSE notifications with a polling fallback, a five-minute proof window, and explicit error/stale states. Render acknowledgements are client-reported; clock synchronization and an actual collector sent-ID comparison are necessary for defensible latency/loss claims. The local egress screen remains synthetic until the edge-owned local UI is integrated. The edge branch has merged local aggregation and policy; joint end-to-end validation remains. See [the API contract](../../contracts/api.md) and [architecture](architecture.md).

Validation on this branch includes local PostgreSQL tenant isolation, idempotency, actions, lineage, enrollment, and separate-region tests. These are synthetic integration tests; organizer-stream, TLS, full failover and target latency still require a joint live run.

## Small local load probe

On 20 November 2026, a local synthetic probe on this development machine sent 20 payloads from one collector and one tenant with four client workers: 20 accepted, zero failed, 0.419 seconds total (47.78 accepted requests/second), client-observed p95 0.1398 seconds. The dashboard and local Postgres were running at the same time. This is a tiny smoke measurement, not an end-to-end latency result, a failover test, or a production capacity claim. Run `python -m saas.tools.loadtest --help` with a private test-only credential file to measure a larger controlled setup; tenant advisory locks serialize requests from the same tenant.
